## What the demo is

The room learns what an agent is by finding an answer in a chart themselves, then building an agent that finds it, on
synthetic patients with heart failure. The quality task is CMS144 (beta blockers in heart failure with reduced
ejection fraction). It is a web page (`demo_pi/public/`, plain HTML/JS/CSS) backed by `demo_pi/server.mjs`. The
server runs a real agent harness, pi (`@earendil-works/pi-coding-agent`), one process per patient, against a small
FHIR server over 100 synthetic patients (`demo_pi/ehr/`). The model is any OpenAI-compatible endpoint; it currently
runs on OpenAI's `gpt-6-luna`, set in `.env` (never in the repo).

The page has eight views:

1. **Overview**: three tiles, "Build an agent → Try it on Rosa → Run it on 100 patients". No subtext.
2. **Task**: the data (record types in a data lake or the EHR, 100 synthetic patients) and the task as a flow:
   on a beta blocker that counts? a documented reason not to be? otherwise a care gap.
3. **Chart**: a mock EHR to find the answer in Rosa's chart by hand, with *Show the answer*. It comes first so the
   room does it themselves before the agent does. The question is fixed to Rosa Delgado; no patient picker (Bruno:
   "don't make me pick the patient's name"). `/api/chart?patient=` still serves any of the 100.
4. **Data**: pick what the agent can see, nine cards; each is a FHIR scope on the agent's token. Each adds informal
   "IRB review" weeks.
5. **Tools**: pick what it can do, nine cards. Three are stand-ins that act outside the chart and are mixed in among
   the others: message the patient, search the web, place orders. Each adds informal "IT setup" weeks.
6. **Prompt**: write a prompt and run the agent on Rosa: her answer, two checks against her chart, and a terminal
   with everything the model is given and does.
7. **Criteria**: tick what counts (CMS144's numerator and valid exceptions), appended to the prompt as sentences.
8. **Test**: run on all 100 patients: a square per patient (green right, red wrong; hover and click to inspect), a
   small window per running agent, Stop, a score and two bars.

**Answers and scoring.** The agent hands in its answer with `submit_answer`, a deliberately general tool: free-text
`answer_1`, `answer_2`, … with nothing about the task in it. The *Structured answer* card adds constrained options
after each answer's words (`option_1` yes/no, `option_2` one of four "why" categories). Each patient is checked on
two answers against the label its chart was generated with: **care gap?** and **why?** (on a beta blocker /
medical reason / patient declined / no documented reason). Free text is read by one more model call that sees the
question and the answer, never the chart (`agent/grade.mjs`). Rosa (patient `p000`) had carvedilol stopped for
Mobitz II heart block, and only her notes say why. That is the core teaching case: without notes the agent says
"care gap", which is wrong.

**Recorded runs** (`demo_pi/recorded/`) let the page replay without a model. They go stale whenever
`ehr/patients.mjs` or `agent/instructions/` change; then `npm test` fails until you re-record (`just demo-record`).
A full re-record costs about 1.5M tokens. Results are cached per build in `demo_pi/.cache/`. The cache key covers
the model, the build, the system prompt, the cohort and the tools' code.

Latest recorded numbers (gpt-6-luna; the "test build" has medications, diagnoses, vitals, notes and allergies, and
the three read tools):

| Prompt | Right of 100 |
|---|---|
| "Is this patient on a beta blocker?" | 50 (the on-treatment half; "not finished" for the rest) |
| "Is there a beta-blocker care gap for this patient? Why or why not?" | 85 (earlier run: 83) |
| + every criterion | 98 (earlier: 100) |
| + every criterion, structured answer, quote check, confidence | 96 (earlier: 97) |

Runs vary by about 3 points from run to run.

## How Bruno steers: keep to these

These are Bruno's instructions from the sessions, in substance. Treat them as requirements.

**The guided presentation is very simple.**
- Minimal words on the main views. No subtext, no explanatory sentences, no helper text ("Not a question about the
  measure, so there is nothing to check…" was removed for exactly this reason).
- Don't put things on screen that the room doesn't need. Earlier versions showed the chart's reason, a quote check,
  a confidence bar and "how it was read" on the answer card; Bruno called it confusing and unnecessary. The answer
  card now shows the agent's answer, two checks and one stats line.
- Results stay simple: the score and two bars. A "what it got wrong" list was removed; people inspect by clicking
  the squares.
- Don't greet people with complexity: the under-the-hood panel starts closed, and a curved arrow points at its
  button after Start until someone opens it.

**Under the hood is where the complexity goes, and it shows raw output.**
- The panel and the logs show programmatic output: requests, responses, JSON, `key: value` lines, tool calls. No
  prose we wrote to explain things.
- Keep a clear visual line between what you are setting up (token scopes, the tools given, the criteria) and an
  example of what it does (Rosa's request and what the model reads).
- It should look like code, not like the main views: no rounded cards or boxes. Section titles are `# setup` and
  `# example · p000 · …`, labels are `// comments`, and a solid rule (setup) or a dashed one (example) runs down the
  left.
- The terminal colours: blue is what the model writes, purple its handed-in answer, grey what comes back.

**Don't leak the task, and make complexity earn its place.**
- The naive prompt ("Is this patient on a beta blocker?") must not come out right by accident. It once did because the
  structured answer's fields asked both questions; that is why `submit_answer` is now general. Watch for any tool,
  schema or instruction that hands the agent the task.
- Each thing the room adds (data, tools, prompt, criteria, structured output) should visibly change the result.
  Leaving it out should get some patients wrong, and giving the agent the proper cues should get (nearly) all of them
  right. If adding something doesn't improve the numbers, question whether it belongs.
- Structured output matters, but the constrained options appear only when that card is on.
- Don't anchor on silly things. Simplify the cases and notes rather than add special-case wording. When you change
  the cohort, notes, criteria or prompts, **test on the live model** and look at what it got wrong before claiming
  anything (`npm test` only checks plumbing with a regex stand-in model).

**Look and feel: the PowerPoint's.**
- A black stage, Apple dark-mode greys, Arial (Helvetica Neue on the web), Font Awesome icons inlined as SVG.
- Each colour means one thing: blue the model, purple its answer, green right, red wrong (Bruno asked for red, not
  orange or yellow). Everything else is white or grey.
- The header reads "QCOR 2026 agent demo" with the CarDS Lab logo. The FHIR logo sits next to "Pick what the agent
  can see", not in a callout. Scrollbars are dark.
- Check the layout at projector size (1280×720) as well as on a laptop.

**Interaction choices he made.**
- Footer icons appear as cards are picked; clicking one takes it away, so the room can rerun and see the effect.
- The 100-patient run has Stop. There is a token counter in the header (be realistic about token use).
- Data cards: family history, social history and appointments were removed. Insurance and immunizations stay as
  distractors that cost IRB time. CMS144 is named only under the hood, not on the slides.
- "Next appointment?" stays as an example prompt, to show the same agent answering a different question.

**Process.**
- Follow `AGENTS.md`: pull first, small commits, commit only when asked, co-author trailer.
- Bruno tests on Railway from `main`. Work on a branch (or a worktree) and push to `main` only when he asks; never
  while the hosted demo is in use.
- Don't make drastic changes. Make the change he asked for, show it, and let him decide on anything bigger
  (infrastructure, scoring, flow).
- Keep READMEs and `NOTES.md` current when behaviour changes: dated entries in `NOTES.md`, and numbers only from
  runs you actually made.

## Latest changes (branch `demo-simplify`, not on `main` yet)

- The panel restyled as code (above). The chart question fixed to Rosa Delgado.
- Failures show their raw error: `error <status>: <message>` at the end of a run's log, and under the test's score
  (`N × timeout: …`, `error: 429 …`), from `summary.errorTop` in `score.mjs`.
- With the structured card on, the agent once handed in `answer_2: "medical reason"` without `option_2` and scored
  "not finished" despite the right answer. Now `submit_answer` refuses a worded answer without its option (a tool
  error; the agent hands it in again), and scoring also accepts a worded answer that is exactly one of the options.
  Live on Rosa with every card on: 6 of 6 right, one after a refused first hand-in.

## Railway: slow or failing runs (tested 4 Nov)

Bruno saw slow, failing runs on Railway with `DEMO_CONCURRENCY=32` and `DEMO_MAX_TOKENS=400` (both as
`docs/hosting.md` recommends) and a different API key from the one in the dev container. In the dev container, the
same code and variables on our key: Rosa right in 6 s, 32 patients 32/32 right in 16 s; pinned to one CPU, still
32/32, in 30 s. The run he was looking at had data cards but no tools (`--tools submit_answer`), so "Unable to
determine" was the right answer; with tools on it works on Railway too. If runs do fail there, read the raw error
now shown under the score: `429` means the key's rate limit (compare its `x-ratelimit-*` headers with ours, 2M tokens
and 5,000 requests a minute), a killed process or timeouts point at the instance (32 sessions need about 3 to 3.5 GB).

## Open items worth cleaning up

- With fixed options on, the naive prompt can still pick a "why" option, because the options show the categories.
  Scoring ignores it (only the questions the prompt asked count), but the behaviour is a mild leak.
- Which questions the prompt "asked" is a regex on the prompt (`score.mjs`: `gap`, `why`/`reason`). It's fragile; a
  cleaner rule would be welcome.
- Structured answers sometimes score a point or two below free text (model slips with thinking off). The words come
  before the options in the schema to help.
- From the "Open" section of `demo_pi/README.md`: align Rosa's story with the PowerPoint, and load-test the hosting.
- The page has not been checked on phones.
- Every re-record and 100-patient run costs real tokens (roughly 150k to 550k per run). Use the cache, and run the
  smallest test that answers your question (`/api/run` on a few patient ids).
